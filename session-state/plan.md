# 项目分析实施计划

## 分析目标

在不修改生产代码的前提下，全面梳理 `Modbus Assistant` 的现状，包括架构分层、通讯链路、Modbus 协议实现、WPF 页面与 ViewModel、依赖注入、测试覆盖和潜在风险，并形成可执行的改进优先级。

## 事实基线

- 解决方案包含主项目和独立 MSTest 测试项目。
- 主项目目标框架为 `net8.0-windows`，采用 WPF、MVVM、Microsoft.Extensions.Hosting 和 Dependency Injection。
- 页面模块包括通讯连接、Modbus 调试、无协议调试、寄存器监视、报文分析、设备管理和系统设置。
- 通讯基础设施支持串口、TCP、UDP 三种通道，并通过统一的 `ICommunicationService` 向上提供状态、收发和统计事件。
- 项目同时存在自定义 Modbus 帧编解码实现和 HslCommunication 封装服务。
- 测试项目包含协议、字节工具、通信、导航/DI、原始调试 VM 等测试文件。
- 调试构建目前被正在运行的主程序进程锁定目标 exe，构建需要先关闭进程后才能得到可靠基线。

## 改进意见与优先级

### P0：统一通信与 Modbus 协议链路

- 将已打开的 `ICommunicationService` 通道作为唯一物理连接源，不再让 `HslModbusService` 单独打开串口/TCP/UDP。
- 原因：连接页维护一套通道状态，Modbus 调试和寄存器监视又维护另一套 Hsl 连接，容易出现“页面显示已连接，但调试页未能发送”的割裂状态。
- 建议：让 Hsl 客户端改为在现有字节流通道上收发，或保留 Hsl 进行协议封装、但显式统一连接生命周期与地址切换。
- 涉及文件：`Services/CommunicationService.cs`、`Services/HslModbusService.cs`、`ViewModels/Pages/ModbusDebugViewModel.cs`、`ViewModels/Pages/RegisterMonitorViewModel.cs`。

### P0：修复 TCP 重连中的递归与资源竞争

- `ReconnectLoopAsync` 调用 `OpenAsync` 时可能再次进入重连逻辑；同时重连成功后原读循环、关闭旧资源和新资源切换没有统一资源所有权。
- 建议：拆成清晰状态机：`Connecting -> Connected -> Faulted -> Reconnecting -> Connected/Disconnected`，重连只负责建立新 `TcpClient`，不得递归调用完整的 `OpenAsync`。
- 在切换或关闭前取消读取循环，等待任务结束，再释放流和 socket；避免 500 ms 超时后直接丢弃任务。
- 涉及文件：`Communication/Tcp/TcpClientChannel.cs`、`Communication/Abstractions/ChannelBase.cs`。

### P1：补强协议边界与解析正确性

- 建议为 RTU、TCP、ASCII 响应解析增加统一最小长度、协议头、长度字段和站号/事务号校验。
- 当前请求构造只覆盖单寄存器和普通读请求，文档提到的写多寄存器、写线圈等功能码尚未形成完整请求构造链路。
- 建议明确每个功能码的请求/响应结构，补充异常响应、截断帧、噪声帧、跨包帧和非法数量边界测试。
- 涉及文件：`Protocol/Modbus/ModbusFrame.cs`、`Protocol/Modbus/ModbusException.cs`、`ViewModels/Pages/ModbusDebugViewModel.cs`。

### P1：增强 Modbus 调试行为与轮询可靠性

- 避免轮询循环在 `ReadOnceAsync` 内重复切换 `IsBusy`；建议轮询使用独立的信号量或“正在轮询中”保护，防止重叠读取。
- 当手动停止轮询时，取消令牌应立即取消正在等待的延时和网络操作，而不是只能等待当前读取结束。
- 轮询失败时应采用退避策略并保留最后成功数据，而不是把异常只写入状态文字。
- 涉及文件：`ViewModels/Pages/RegisterMonitorViewModel.cs`、`ViewModels/Pages/ModbusDebugViewModel.cs`。

### P1：降低生命周期与线程模型风险

- `App` 使用静态只读 Host，在测试和宿主重启场景中不易重建；全局异常处理应记录结构化日志并区分致命/可恢复异常。
- 通信事件回调由后台线程触发，部分只在主窗口和页面层做了 UI 线程切换，建议统一在服务边界或订阅基类中明确线程约定。
- `Dispose` 同时触发异步断开但不等待，可能在进程退出时留下未完成资源释放；建议由 Host `StopAsync` 显式关闭所有通信服务。
- 涉及文件：`App.xaml.cs`、`Services/CommunicationService.cs`、`Services/ApplicationHostService.cs`、各通信通道。

### P1：补齐持久化、配置与服务器一致性

- 设备方案导入导出、系统设置和服务器寄存器没有看到统一持久化抽象，建议集中到配置服务并校验版本和数据范围。
- Modbus 服务端应在启动前校验地址重叠、寄存器容量和站号；停止后应释放端口并明确启动失败原因。
- 涉及文件：`ViewModels/Pages/DeviceManagementViewModel.cs`、`ViewModels/Pages/SettingsViewModel.cs`、`Services/HslModbusServerService.cs`、`ViewModels/Pages/ConnectionViewModel.cs`。

### P2：提高测试的真实行为覆盖

- TCP 测试依赖回环监听，UDP 测试可用于确定收发；应继续增加串口模拟或抽象串口适配器，避免硬件依赖。
- 测试应覆盖连接切换时旧通道释放、发送失败、对端 EOF、重连取消、TCP 分包、跨包组合和协议异常响应。
- 使用伪造 `ICommunicationService/IChannelFactory` 验证 ViewModel 和通信服务隔离，而不是主要依赖真实 socket。
- 涉及文件：`tests/Yuandl.ModbusAssistant.Tests/CommunicationTests.cs`及其他测试项目源码。

# Modbus 服务器多寄存器数据支持计划

## 需求理解

用户希望 Modbus 服务器能够建立并管理多个不同地址、不同数据含义的寄存器，而不是仅支持一个地址对应一个 ushort。当前实现已有保持寄存器地址、初始值和备注的界面，但缺少类型、字节序、位宽、只读/读写和重叠校验。

## 建议范围

- 第一阶段实现保持寄存器、输入寄存器、线圈和离散输入四类区域。
- 数据类型支持布尔、Int16、UInt16、Int32、UInt32、Float、Double。
- 保持初始值可由用户在界面直接编辑，并支持运行时由客户端通过功能码写入。
- 支持地址重叠校验、跨地址连续性校验、数据类型位宽校验和只读区域校验。
- 支持 JSON 保存、加载、导入和导出；先复用现有设备管理能力的位置或建立独立配置服务。

## 数据模型

- 新增 `ServerRegisterDefinition`
  - `RegisterArea`：Coil、DiscreteInput、InputRegister、HoldingRegister
  - `Address`：ushort 区域内起始地址
  - `DataType`：Bit、Int16、UInt16、Int32、UInt32、Float、Double
  - `ByteOrder`：BigEndian、LittleEndian
  - `InitialValue`：字符串化值，便于编辑和持久化
  - `Note`：备注
  - 当前访问权限由区域决定：输入寄存器/离散输入只读，保持寄存器/线圈可写
  - `RegisterCount`：根据类型自动计算占用寄存器数

- 用独立的寄存器表维护配置，而不是把业务类型折叠到一个 ushort 值。
- 保持不同寄存器定义互不覆盖；例如 Float 从地址 100 开始占用 2 个寄存器。

## 服务层修改

- 在 `HslModbusServerService` 中新增寄存器定义注册和移除能力。
- 将配置写入拆为按区域的操作：
  - 写保持寄存器
  - 写输入寄存器
  - 写线圈
  - 写离散输入
- 向服务器提交寄存器值时统一做类型编码、字节序转换和地址边界校验。
- 启动前检查：地址非负、站号有效、端口有效、定义不重叠、各区域数量不超过地址空间。
- 停止后清除运行态引用，不清除用户配置表。
- 增加读取或更新单个寄存器定义的能力，以便界面实时同步。

## ViewModel 修改

- 将现有 `ServerRegister` 记录扩展为完整数据定义。
- 增加属性：寄存器区域、数据类型、字节序、访问模式、初始值、只读状态。
- 增加命令：建立、编辑、删除、批量导入、导出、保存配置、加载配置。
- 建立寄存器时根据选择的类型自动计算占用寄存器数量并预校验地址重叠。
- 操作成功后刷新列表；操作失败只通知具体校验或服务器异常，不做静默成功。

## 界面修改

- 在“保持寄存器配置”中按区域展示或拆分为四个页签：保持寄存器、输入寄存器、线圈、离散输入。
- 列表显示：区域、起始地址、数据类型、字节序、占用长度、当前值、访问模式、备注。
- 为地址和初始值增加绑定更新及输入校验提示。
- 提供删除所选寄存器、保存配置、加载配置按钮。
- 保持服务器启动卡片与寄存器管理卡片状态一致。

## 持久化

- 配置文件格式使用带版本号的 JSON。
- 顶层包含端口、站号、寄存器定义集合。
- 保存时排除运行时派生值，只保存地址、区域、类型、字节序、初始值、访问模式和备注。
- 加载时先校验文件版本、枚举值、地址范围和重叠，再应用到服务器或 UI。
- 建议默认存放在应用数据目录，并允许用户选择任意文件路径导入导出。

## 测试计划

- 数据类型编码和解码：布尔、16 位、32 位、64 位、Float、Double。
- LittleEndian 和 BigEndian 编码一致性。
- 重叠地址、超出 65535、无效站号、非法端口、空寄存表测试。
- 保存、重启、加载配置后值和地址一致性测试。
- 客户端读取保持寄存器、输入寄存器、线圈和离散输入。
- 客户端写保持寄存器、写线圈后服务器模型立即更新。
- 删除或修改运行中寄存器时的行为和异常提示。

## 实施顺序

1. 扩展服务端寄存器定义与重叠校验。
2. 完成类型编码和区域映射。
3. 修改连接页 ViewModel 与界面。
4. 增加 JSON 持久化。
5. 补充协议与界面回归测试。

## 实施状态

- 已将服务端寄存器存储实现为独立 Modbus TCP 数据区，不依赖 HslCommunication 对输入寄存器的内部映射。
- 支持保持寄存器、输入寄存器、线圈、离散输入；数值类型支持 Bit、Int16/UInt16、Int32/UInt32、Float、Double。
- 支持地址范围和重叠校验、输入区只读、客户端写入保持寄存器/线圈、运行时编辑定义以及版本化 JSON 自动保存和导入/导出。
- 注意：当前所谓“运行时编辑”仅通过变更定义的初始值重置服务器数据；列表展示的是 `InitialValue` 而非服务器当前运行值，也没有选择已有定义后自动载入编辑表单，因此缺少可靠的在线值修改与反馈体验。
- TCP 服务端支持标准功能码 01/02/03/04/05/06/0F/10。
- 新增数据区编码、配置 JSON、真实回环 TCP 服务器测试；测试项目共 30 项全部通过。
- 因应用正在调试，使用 `bin\\Verify` 独立输出构建和运行测试；需重启正在运行的应用以加载修改。
- 当前每项寄存器的访问权限由区域固定决定，尚未提供逐项 ReadOnly/ReadWrite 配置。

## 暂定假设

- 第一阶段使用 0 至 65535 区域地址。
- 输入寄存器和离散输入只读；保持寄存器和线圈可写。
- `Double` 占用 4 个寄存器，Float 占用 2 个寄存器，32 位类型占用 2 个寄存器。

# 无协议服务器收发功能计划

## 对现状的判断

可以实现无协议服务器监听并发送，但当前代码尚不具备该能力：现有 `TcpClientChannel` 是主动连接远端的 TCP 客户端，`UdpChannel` 也是面向配置远端的 UDP 通道；无协议调试页面通过统一通信服务向当前活动通道发送字节。因此需要增加服务器侧通道，而不是仅在界面增加“监听”按钮。

## 建议的第一阶段范围

- 先实现 TCP Server：配置本地监听地址和端口，异步接收多个客户端连接及原始字节流。
- 无协议调试页显示当前连接客户端列表，用户选择一个客户端后可发送原始 HEX/ASCII/UTF-8 数据。
- 明确 TCP 是字节流，不保证一次接收对应一次发送；界面保留原始接收块和时间戳，不宣称具有报文边界。
- 断开单个客户端时只移除该客户端，不影响监听服务及其他客户端。
- 服务器停止时取消 accept/receive 循环、释放所有 socket 并更新连接状态。
- 沿用现有发送编码、结束符、历史记录、循环发送、暂停接收和消息保留上限。

## 架构改动建议

- 新增 `TcpServerChannel`，管理监听 socket、客户端会话、接收事件、定向发送和客户端连接/断开事件。
- 由于当前 `IChannel`/`ICommunicationService` 假设单通道且 `SendAsync` 不指定目标，需要为服务器客户端目标提供类型安全的会话 ID 和发送接口；避免把客户端标识塞进字符串或用全局静态状态。
- 扩展通道工厂、连接 ViewModel 和连接页面以配置、启动、停止 TCP 监听。
- 在 `DataReceivedEventArgs` 或服务端专用事件中携带会话 ID，使 RawDebug 页面能够显示数据来自哪个客户端。
- 无协议发送命令在服务端模式下必须要求选择客户端；无目标时明确提示，不得静默发送或默认广播。
- 在应用宿主关闭时停止监听并等待客户端会话释放。

## UDP 扩展（后续可选）

- UDP Server 绑定本地端口，接收数据报，并将发送目标定义为“指定远端”或“最近一次对端”。
- UDP 是数据报协议，应保留每个数据报边界；与 TCP 客户端选择模型分开处理。
- 不把 TCP Server 的客户端会话语义直接套用到 UDP。

## 测试与验证

- 回环测试验证服务器监听、两个客户端连接、每个客户端独立收发和定向发送。
- 验证关闭单个客户端不影响其他会话，停止服务器会取消接收循环并释放端口。

# Modbus 服务器在线修改寄存器值计划

## 当前问题分析

已直接检查当前代码，确认用户仍无法直观在线修改，原因不止一个：

- 服务器运行值存放在 `HslModbusServerService` 的线圈、离散输入、输入寄存器和保持寄存器数组中，但该服务没有供界面在线读写值的 `GetValue/SetValue` API。
- UI 的“添加/更新”只更改定义中的 `InitialValue`，没有修改按钮所表达的运行态写值语义。
- 列表绑定 `InitialValue`，客户端通过功能码写入后列表不会显示当前运行值。
- `SelectedServerRegister` 只绑定列表选中项，没有 `OnSelectedServerRegisterChanged` 回填表单；用户选中后不能编辑加载现有定义。
- 定义是不可变 record。当前按钮通过相同区域和起始地址覆盖配置项，但只能改元数据/初始值，不是专门的在线写操作。
- 前次修改时说明了运行中的 WPF 实例未热加载变更、需重启；如果用户仍在旧实例中验证，旧界面/命令自然不会体现后来代码。本次需在实现和验证步骤中明确重启应用，避免只检查旧进程。

## 目标行为

- 服务器运行期间，用户能选中已有数据定义、查看当前值、输入新值并立即写入服务端存储。
- Modbus 客户端下一次读取时得到新值，无需停止/重启服务器。
- 客户端写入保持寄存器或线圈后，UI 能刷新并展示客户端写入后的值。
- 输入寄存器和离散输入保持只读；用户可在线修改其模拟输入值，但外部 Modbus 客户端不能写入。
- 在线改值只改运行态值，不覆盖定义的初始值；停止并重新启动时按配置的初始值恢复。

## 实施方案

1. 扩展 `HslModbusServerService`
   - 增加 `SetValue(area, address, value)`，将文本值按数据类型/字节序编码后写入对应数组。
   - 增加 `GetValue(area, address, dataType, byteOrder)`，按当前数据区值解码为可显示字符串。
   - 将客户端写入时对原始寄存器数组的更新纳入同一同步锁，避免 UI 刷新或编辑期间读取到部分写入状态。
   - 保持现有限制：客户端只可写已定义的保持寄存器/线圈；输入寄存器/离散输入仅允许本地 UI/API 改值。

2. 扩展 `ServerRegisterCodec`
   - 新增解码路径，覆盖 Bit、Int16、UInt16、Int32、UInt32、Float、Double 及 LittleEndian。
   - 对输入字符串执行严格数值解析；无效输入时保留原值并明确提示。

3. 更新 `ConnectionViewModel`
   - 选中定义后自动填充区域、地址、类型、字节序、当前值和备注。
   - 区分“新增/修改定义”和“应用当前值”两个操作。
   - 应用当前值成功后立即刷新列表；失败时保留当前输入并提示具体原因。
   - 服务器运行时仍允许更改；配置初始值与实时值分别保存/展示。

4. 更新 `ConnectionPage.xaml`
   - 列表增加“当前值”列，不再将初始值误当成实时值展示。
   - 增加“应用当前值”按钮和明确的运行时状态提示。
   - 选中行时编辑区展示值，确保用户能直接选择、编辑、提交。

5. 处理刷新
   - 提供明确的手动刷新命令。
   - 为反馈客户端写入，采用低频 UI 定时刷新（如 250–500 ms），并在页面不活跃或服务器停止时暂停，避免无意义轮询。
   - 只更新当前值列，不覆盖用户正在编辑的输入框。

## 验证

- 服务层测试：运行中更新不同类型数据后通过 TCP 读取功能码 01/02/03/04 得到新值。
- 反向测试：客户端写保持寄存器/线圈后 `GetValue` 返回更新值；输入区仍拒绝客户端写入。
- 测试无效数值不改变服务器运行值，LittleEndian 32/64 位往返正确。
- UI/ViewModel 测试：选择记录填入字段、在线应用值、刷新不覆盖输入、初始值与当前值语义分离。
- 停止并重启后当前值恢复到持久化初始值。

## 暂定产品行为

- “在线更改”同时指本地界面修改服务器当前值，以及将客户端写入的保持寄存器/线圈值实时显示在界面。
- 输入寄存器和离散输入允许本地模拟器改值，但客户端仍只读。
- 在线改值不写回配置初始值；重启时恢复初始值。
- 实施时将编辑流程明确拆分为“新增定义”“更新定义”“应用当前值”，选中既有定义后必须填充编辑表单。
- 重新构建、运行新的测试后，明确提示并执行关闭旧 WPF 实例、启动新版本验证；不把旧进程界面当作代码未生效的判断依据。
- 本轮仅更新计划，没有修改源代码；由于无法获得用户澄清，按以上完整行为继续规划。

# 通讯连接页面内容过多、滚动查看问题计划

## 当前结构与初步判断

- `Views/Pages/ConnectionPage.xaml` 已有外层 `ScrollViewer VerticalScrollBarVisibility="Auto"`，页面主体为包含 5 个自动行的 Grid。
- 页面内容包含页面说明、串口/TCP/UDP 参数卡片、连接状态控制、服务器配置和数据区列表；窗口较矮时整体内容超过可视高度是预期情况。
- 数据区配置中的 `ListView` 有固定高度并自带内部滚动条；鼠标位于该列表时，滚轮会优先滚动列表，而不是外层页面，用户可能因此误以为整页无法滚动。

- 在窗口正常及最小尺寸下，连接页面每个区域均能通过鼠标滚轮和拖动滚动条访问。

- 不改变串口、TCP 客户端、UDP 和 Modbus 服务器的现有功能及绑定。

3. 检查固定高度 ListView 的滚轮行为；若它截获外层滚轮，则为列表提供明确的独立滚动体验，或在滚动到列表边界时将滚轮继续传递给页面。避免简单移除列表内滚动而造成大量数据时控件无限扩张。
4. 在通讯连接卡片之间保留清楚间距，服务器配置放在页面下方并可通过整页滚动到达；若页面纵向内容仍过长，可将服务器配置折叠/独立区域化，但不隐藏核心连接操作。
5. 验收场景包括窗口 1280x820、窗口最小尺寸 960x620、连接页底部服务器配置、寄存器列表内部滚动、滚动条拖动和鼠标滚轮滚动。

- 寄存器列表增加滚轮处理：列表内部可滚动时继续滚动列表；到达列表顶部/底部后，将滚轮滚动传递给整页。
